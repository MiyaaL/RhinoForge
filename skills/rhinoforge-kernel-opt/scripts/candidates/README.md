# Clean-room RPU source candidates

The source snapshots referenced here live in the external candidate directory
`/home/hx/miyaa/work/src/rhinoforge-rpu-candidates-20260903`; they are not part
of the RhinoForge Git tree.  They are authored RPU C/C++ (`.rc`) candidates,
not copied from, disassembled from, or patched versions of the installed
operator-library asset.  The hxcc compiler necessarily emits an opaque `.ref`
so Rhino Launch can execute a candidate; that generated file is a disposable
load artifact, not the implementation and is never checked in.

## How to classify a result

* `release baseline`: the harness loaded the owner-supplied release `.ref`.
  This establishes the production ABI and a regression comparator only.
* `source-derived diagnostic`: the harness loaded a `.ref` generated by hxcc
  from one of the `.rc` files below in a private directory.  The result is
  valid only for the exact source hash, compiler flags, shape, and ABI stated
  in the receipt.
* `release candidate`: requires the release owner to admit the symbol,
  parameter/grid ABI, manifest entry, signed asset, and held-out profile.  No
  file in this directory has reached that state.

For every source-derived run, preserve the source SHA-256, hxcc/toolchain
receipt, assembly inspection JSON, parity result, and native/host timing in an
external evidence store.  Keep `.ref`, `.o`, `.s`, `.bc`, `.rci`, traces,
weights, and addresses outside Git.

(`RF_N_TILES=2,RF_GROUPS=4`) and `35.305 us`
(`RF_N_TILES=4,RF_GROUPS=2`) in separate fresh processes.  The native ordering
and host-p50 ordering disagree, so the difference is treated as board/launch
noise rather than proof that either compile flag is globally optimal.

## Reproduction skeleton

Use the source-first procedure in the parent skill.  In particular, preserve
the source basename when invoking hxcc, inspect the generated assembly before
timing, and run the board command through the canonical lease:

```bash
src=/home/hx/miyaa/work/src/rhinoforge-rpu-candidates-20260903/gemm_ddr_col_m32n256k1024_acc32.rc
build=$(mktemp -d /dev/shm/rhinoforge-rc-XXXXXX)
cp "$src" "$build/$(basename "$src")"
(cd "$build" && hxcc -O2 -save-temps -DRF_N_TILES=4 -DRF_GROUPS=2 \
  -c "$(basename "$src")")
python skills/rhinoforge-kernel-opt/scripts/inspect_rpu_asm.py \
  "$build"/*-host-rpu-rhino-rpuhsa.s --source "$build/$(basename "$src")" \
  --require-entry --strict --require-vmat --require-lpaddr \
  --require-async-fence
bash skills/rhinoforge-kernel-opt/scripts/build_pure_gemm_bench.sh \
  "$build/pure_gemm_bench"
python skills/rhinoforge-kernel-opt/scripts/board_lease.py -- \
  sudo -n env "$build/pure_gemm_bench" \
  --binary "$build/gemm_ddr_col_m32n256k1024_acc32.ref" \
  --kernel gemm_ddr_col_m32n256k1024_acc32 --m 32 --n 2048 --k 1024 \
  --partition 1 --cores 8 --acc32 --tile 128 --typed-weight \
  --warmup 5 --iters 40
rm -rf "$build"
```

The production-shaped SiLU and residual sources need separate four-pointer
host harnesses: the former allocates two transformed `HostDDR_t` weights and
binds `regs6/7` to the second weight; the latter binds `regs6/7` to a per-core
SPM residual slice.  The checked-in SiLU verifier is
`full_silu_ddr_multicore_runner.cpp`; the residual verifier used the same
broadcast protocol in the external diagnostic workspace.  Until either
packet is assigned a release-owned ABI and manifest name, its board result
remains diagnostic even when parity passes.
